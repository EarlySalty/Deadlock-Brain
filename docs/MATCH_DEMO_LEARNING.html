Standardablauf

Der Pilot katalogisiert alle verfügbaren Mo-&-Krill-Matches des Referenzspielers. Siege und Niederlagen bleiben enthalten; die Auswahl ist nicht auf den aktuellen Patch begrenzt.

./rust/target/release/deadlock-brain player sync-matches 281768392 --hero-id 18 --pretty
./rust/target/release/deadlock-brain player fetch-demo 281768392 <MATCH_ID> --hero-id 18 --steam-id64 76561198242034120 --pretty
./rust/target/release/deadlock-brain player analyze-demo-match 281768392 <MATCH_ID> --pretty

fetch-demo lädt zuerst vollständige Match-Metadaten und danach drei Demo-Queries: Player-State, zielspielerbezogene Combat-Ereignisse und Economy/Objectives. Ein fertiger Evidenz-Snapshot entsteht nur, wenn alle drei Queries erfolgreich sind.

Dry-Run

./rust/target/release/deadlock-brain player analyze-demo-match 281768392 <MATCH_ID> --dry-run --pretty

Der Dry-Run baut und persistiert nur den Kontext mit Status context_ready. Es gibt keinen Fireworks-Aufruf und keinen fertigen Report.

Menschliches Review

Entscheidungs-IDs stehen im Markdown als D1, D2 usw. Das Review wird aus einer Datei gelesen; freies Shell-JSON wird nicht akzeptiert.

{
  "reviewed_decision_ids": ["D1", "D2", "D3", "D4", "D5", "D6", "D7"],
  "corrections": [
    {
      "decision_id": "D1",
      "label": "unbelegt",
      "comment": "Der Beleg zeigt das behauptete Ereignis nicht.",
      "replacement": "Nur die beobachtbare Zustandsänderung beschreiben."
    }
  ]
}

reviewed_decision_ids muss alle kanonischen IDs des Reports enthalten; nur corrections darf eine Teilmenge sein. Erlaubte Labels: falsch, unbelegt, Kontext fehlt und wichtige Entscheidung uebersehen. Die angegebene Note-ID wählt den geprüften Report; gespeichert werden zusätzlich dessen Context- und Report-Hash.

./rust/target/release/deadlock-brain player review-demo-report <NOTE_ID> --file review.json --pretty
./rust/target/release/deadlock-brain player demo-calibration-status 281768392 --pretty

Kalibrierungstor

  • Mindestens fünf unterschiedliche Reports müssen geprüft sein.
  • Die letzten drei Reports dürfen keinen kritischen Fehler enthalten.
  • Die Korrekturquote jedes dieser drei Reports muss strikt unter 10 Prozent liegen.
  • falsch, unbelegt und wichtige Entscheidung uebersehen sind immer kritisch. Kontext fehlt ist kritisch, wenn eine Ersetzung die Entscheidung ändert.

Nur das Gate berechnet den Kalibrierungsstatus. Eine Modell-Selbsteinschätzung kann ihn nicht öffnen.

API-Limits und Fehler

Die Deadlock API veröffentlicht Limits endpointabhängig und signalisiert Überschreitungen mit HTTP 429; für den Demo-Query-Endpunkt ist keine feste öffentliche Quote dokumentiert. Der Pilot startet deshalb genau drei Query-Jobs pro Match nacheinander, pollt standardmäßig alle 5 Sekunden und wartet pro Job höchstens 900 Sekunden.

Ein Poll-GET hat genau einen inneren HTTP-Versuch. 429, Server- und Transportfehler werden in der Poll-Schleife wiederholt; Anfragezeit, Backoff und Poll-Pause bleiben innerhalb der Gesamtdeadline. Ergebnisdaten werden nur direkt per HTTPS von demo-extracts.deadlock-api.com geladen; Redirects oder andere Origins werden abgelehnt. Ein Demo-Submit wird nicht blind wiederholt, weil ein POST trotz verlorener Antwort bereits einen Job erzeugt haben kann. Fehler bleiben sichtbar, und ein unvollständiger Lauf erzeugt keinen fertigen Evidenz-Snapshot. Quelle: Deadlock API Reference.

Steam-Fallback

Fehlt eine Demo in der API, bleibt das Match offen und das nächste verfügbare Match kann analysiert werden. Der direkte Game-/Steam-Download ist bewusst vertagt, bis mehrere API-Reports den Evidenz- und Reviewvertrag bestanden haben. Dadurch wird nicht gleichzeitig ein zweiter Demo-Parser debuggt, während der fachliche Reportvertrag noch kalibriert wird.
